# OpenGuardrails-Text-4B-0124 — узкие места и идеи оптимизации

Decoder-guardrail на Qwen3 (4.02B параметров, 36 слоёв, GQA 32/8), fp16, батч 1. Tesla T4 (Kaggle), torch 2.11.0+cu130, transformers 5.20.1 (`env.json`).
Ноутбук: [`notebooks/openguardrails_profile.ipynb`](../../../notebooks/openguardrails_profile.ipynb).

**Важно для воспроизведения.** Промпт строится шаблоном `OpenGuardrails-Text-2510`. Опубликованный шаблон 0124 не содержит инструкции классификатора, и с ним модель отвечает неверно («How can I make a bomb?» → `safe`). Инструкция добавляет ~290 токенов к каждому входу. fp16 проверен против fp32: P(unsafe) совпадает с точностью до 0.003.

## Ключевые цифры

| Текст, токенов | Вход с инструкцией | prefill p50 / p95, мс | вердикт `safe` (generate) p50 / p95, мс |
|---|---|---|---|
| 16 | 306 | 214 / 218 | 271 / 277 |
| 128 | 418 | 282 / 283 | 335 / 338 |
| 512 | 802 | 656 / 664 | 716 / 719 |
| 1024 | 1313 | 1329 / 1335 | 1394 / 1399 |

- Опасный ответ `unsafe\nS5` (5 токенов) на 296 токенах входа: **434 / 451 мс** при prefill 212 мс.
- Один шаг decode — 49–65 мс при нижней границе ~25 мс (чтение 7.5 ГБ весов при 320 ГБ/с).
- Prefill: GPU занята на 96–99%, но достигает лишь ~17% пика T4 fp16; ~2830 ядер на forward.
- Доли времени GPU в prefill (306 → 1313 токенов): matmul 57 → 32%, **attention в fp32** 10 → 27%, elementwise 17 → 23%, copy ~10%, softmax 2 → 6%.
- SDPA на всех длинах идёт через **math-бэкенд**: attention считается в fp32 (`volta_sgemm`) с отдельными ядрами маски.

Скриншоты Perfetto (`figures/perfetto_safe_L16.png`, `figures/perfetto_safe_L512.png`): в prefill GPU занята сплошь, а CPU её опережает. Между prefill и `decode_1` есть синхронизация (`aten::is_nonzero → item → cudaStreamSynchronize`). В decode GPU ждёт, пока CPU запустит ~2800 ядер ради одного токена.

## Узкие места

1. **Длинная постоянная инструкция.** ~290 из 306 токенов минимального входа — одинаковый для всех запросов текст, и он пересчитывается каждый раз.
2. **Prefill упирается в GPU**, причём неэффективно: fp32-attention через math SDPA, много мелких elementwise и копий (RMSNorm, RoPE, SiLU·mul, маски, приведение типов).
3. **Decode упирается в overhead.** На каждый токен ~2800 запусков ядер и проверка остановки с синхронизацией; шаг в 2 раза дольше нижней границы по памяти.
4. **Синхронизации CPU↔GPU.** Одна на forward (`aten::is_nonzero`; вероятный источник — `padding_mask.all()` в `masking_utils` при переданной `attention_mask`) и одна на шаг generate. Мешают CUDA Graphs и `torch.compile(fullgraph=True)`.
5. **Скрытый CPU-предел.** CPU тратит на запуск prefill ~100–130 мс при ~210 мс на GPU. Если ускорить GPU примерно вдвое, узким местом станет CPU.

## Идеи оптимизации

| Идея | Что лечит | Ожидаемый эффект | Без потери качества? |
|---|---|---|---|
| **Кэш префикса инструкции**: первые 227 токенов (до `User:`) одинаковы для любого текста — KV-кэш считается один раз и переиспользуется | узкое место 1 | prefill коротких входов ~80 токенов вместо ~306; оценка — в 2–3 раза быстрее (измерить) | да: те же KV-значения, с точностью до порядка операций в fp16; сверить P(unsafe) |
| **Вердикт по первому токену**: один prefill с `logits_to_keep=1`, P(unsafe) по паре токенов `safe`/`unsafe`; категорию генерировать только для `unsafe` | decode (3) | `safe`: 272 → 214 мс (−21%); бинарный `unsafe`: 434 → 212 мс (−51%) | бинарный вердикт тот же; категория становится опциональной — решение по протоколу |
| **`lm_head` только на 2 строки** (`safe`, `unsafe`) | GEMV по словарю 152K | ~1.5% prefill, меньше памяти | да для P(unsafe) |
| **Efficient-attention вместо math** (fp16-ядро; например, повторить KV-головы без `enable_gqa`, или не передавать маску при батче 1) | fp32-attention и маски (2) | 10–27% + часть elementwise/softmax; растёт с длиной | практически да; сверить P(unsafe) |
| **Убрать синхронизации**: не передавать `attention_mask` при батче 1 без паддинга; свой цикл decode без проверки на каждом шаге | 4 | открывает дорогу CUDA Graphs | да |
| **CUDA Graphs / `torch.compile(mode="reduce-overhead")` со статическим KV-кэшем** (`cache_implementation="static"`) | overhead decode (3), CPU-предел (5) | шаг decode ближе к ~25 мс | да |
| **Слияние операторов** (Inductor или ORT: SimplifiedLayerNorm, Rotary, GroupQueryAttention — проверить поддержку sm75) | elementwise и copy, ~30% prefill | меньше ядер и проходов по памяти | да |

### Как убрать overhead
- Не генерировать лишние токены: вердикт по первому токену.
- Убрать синхронизации внутри forward и между шагами, затем захватить forward в CUDA Graph со статическим KV-кэшем.
- Сократить число ядер слиянием операторов. Это нужно и для prefill, чтобы CPU не стал узким местом после ускорения GPU.

### Как сделать вычисления плотнее
- Не пересчитывать постоянный префикс.
- Перевести attention на fp16-ядро без отдельной маски.
- Слить RMSNorm, RoPE, активации и сложения с соседними операциями.
- После этого заново снять профиль: остаток — GEMM (~17% пика), здесь можно сравнивать cuBLAS, ORT и TensorRT.

## Оговорки
- 50 замеров на длину — p95 грубый; повторных сессий для OpenGuardrails не было.
- Перед частью прогонов GPU была тёплой (66–77 °C) — частоты не контролировались.
- Источник синхронизации в маске — гипотеза по исходникам transformers, не подтверждена стеком вызовов.
- GPU busy и TFLOPS — оценки: время ядер берётся из прогона под профайлером, а задержка — из отдельного прогона.
