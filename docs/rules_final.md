# Финальный набор правил

Только правила, которые дали выигрыш на замерах, и условия их включения. Условия проверяются кодом (`rules/conds.py`), подробности правил — в `optimizations.md`.

## Когда что включать

| Правило | Включать, если | Параметры | Эффект (p95) |
|---|---|---|---|
| **U4** `torch.compile` | всегда | любой batch; разрывы графа (`torch._dynamo.explain`) снижают эффект | batch 16: основной выигрыш, −23…−40% у энкодеров |
| **U1** CUDA graph по бакетам длин | `torch.cuda.is_available()` и batch 1 | только вместе с U4. Входы > 2048 токенов у декодера — только вместе с быстрыми ядрами attention (C7), иначе медленнее | batch 1, короткие входы: −70…−87%; batch 16: ≈ 0 |
| **C7** быстрые ядра linear attention | `"linear_attention" in cfg.layer_types` или есть `*GatedDeltaNet`, и импортируется `fla` | обязателен при входах > 1024 токенов | HaloGuard B4: +17% → −30% |
| **C3** lm_head по двум токенам | `model.can_generate()`, есть `lm_head`, вердикт за один forward | — | +1–2% поверх U1+U4 |
| **C8** кэш относительных позиций DeBERTa | `any(hasattr(m, "get_rel_embedding") for m in model.modules())` | — | batch 1: KoalaAI −24% → −37% |
| **C12** слить Q/K/V и gate/up | у модуля есть отдельные `q_proj/k_proj/v_proj` (или `gate_proj/up_proj`), все `nn.Linear` с одинаковым bias | — | +1–2% |
| **C9** веса в fp16/bf16 вместо autocast | веса fp32, forward идёт под `autocast` fp16/bf16 | — | batch 1: Laya −11% сам по себе |
| **C13** один forward вместо `generate(max_new_tokens=1)` | эталон зовёт `generate` с `max_new_tokens == 1` | нужен как основа: без него к модели не применить U1/U4 | ≈ 0 сам по себе |
| **C4** вердикт по первому токену | эталон зовёт `generate` с `max_new_tokens > 1`, и первый токен совпадает с вердиктом полного ответа | — | p50 −14 мс, p95 ≈ 0 |

## Не включать

| Правило | Почему |
|---|---|
| **C2** кэш префикса | На baseline v4 замедляет: HaloGuard +10…+18%, HiveTraceGuard-Pro до +72%. У HiveTraceGuard-Pro ещё и меняет вердикты (4 из 1600) |
| **U3** убрать синхронизации | При batch > 1 нельзя: маска нужна для паддинга. При batch 1 выигрыш ≈ 0 |
| **U1+U4 через штатный `generate` HF** (статический кэш + `reduce-overhead`) | Open: на 13–26% медленнее baseline |

## В коде: автоприменение в `plan` и `run`

Правила заморожены в `rules/autotune.py`. Тот же файл лежит в CLI как `src/guardrail_tuner/rules.py` (ветка `feat/guardrail-tuner-cli`).

- **`plan`** читает только `config.json`, без весов. `rule_features()` достаёт признаки, `select_rules()` по задаче, устройству и runtime плана решает, что включить. Список правил пишется в `execution.rules`. Рядом в `rules` лежат причины пропуска и нужные пакеты. Это вместо общего fallback на `torch.compile`: compile попадает в план только там, где он доказал выигрыш, и всегда вместе с правилами под архитектуру.
- **`run`** сначала считает ответ eager PyTorch. Потом применяет правила к загруженной модели: каждое перепроверяется по структуре модели, неподходящее пропускается с причиной. Затем снова считает ответ и сравнивает с eager. Если хоть одна метка поменялась, возвращается ответ eager, а правила отмечаются как отклонённые. `serve` применяет правила без сверки, поэтому план нужно сначала проверить через `run`.

| Признак в `config.json` | Задача и параметры плана | Правила |
|---|---|---|
| любая архитектура `*ForSequenceClassification` | `device: cuda` | U4, U1 (U1 только для вызовов с одним входом) |
| — | `device: cpu` | без U4 и U1: на CPU не мерилось |
| `relative_attention: true` или `model_type: deberta` | классификация | C8 |
| отдельные `q/k/v_proj`, `query/key/value_proj`, `gate/up_proj` или `in_proj_*` (проверяется на загруженной модели) | классификация или бэкбон без задачи | C12 |
| `"linear_attention" in layer_types` (в т.ч. в `text_config`) | любая | C7 и пакет `flash-linear-attention` |
| `*ForCausalLM` / `*ForConditionalGeneration` | генерация, `runtime: transformers` | U4 и U1 не включаются: внутри `generate` они медленнее |
| — | `runtime: vllm` | никаких: vLLM сам делает графы и кэш |
| архитектура без задачи (`*Model`) или кастомный код (`auto_map`) | `execution` нет | только правила на модулях бэкбона: C12, по признакам C7 и C8. U4 и U1 пропущены: CLI не знает, какой вызов оборачивать |

C3, C9, C13 и C4 в CLI не вошли. Им нужен контракт вердикта по токенам или SDK модели (Laya), а у общего CLI такого контракта пока нет. В измерителе У1 они остаются в `rules/adapter.py`.

**Проверка.**
- В CLI: тесты `tests/test_rules.py` — выбор правил по конфигам, план через CLI, совпадение с eager на маленьких DeBERTa v1/v2, сквозной `run`. Все 70 тестов CLI проходят, `ruff` чистый, новых ошибок `mypy` нет. На реальных конфигах `plan` выдаёт: KoalaAI и Llama Prompt Guard на CUDA — C12, C8, U4, U1; HaloGuard — C7; HiveTraceGuard-Pro — ничего; AccuKnox Guard 1.1 (бэкбон Qwen3.5 без задачи) — C7, C12. На маленькой случайной Qwen3.5 C12 слил все группы проекций, выход совпал до 5e-7.
- На GPU: CUDA graph и inductor на CPU не проверить. Скрипт для GPU — `rules/cli_check.py`, он сравнивает eager, «только compile» и правила плана при batch 1: `python rules/cli_check.py KoalaAI/Text-Moderation hipocap/Llama-Prompt-Guard-2-22M`. Ещё не запускался.
