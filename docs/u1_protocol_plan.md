# У1: среда и единый протокол

Точка входа с 29 октября 2026. Предварительное профилирование и исследование реализаций завершены; теперь делаем результат роли У1, а не расширяем матрицу оптимизаций. Публикации результатов остаются историческими свидетельствами, не заменяют общий пайплайн.

**Комплект к синку 30 октября подготовлен:** [среда и lock](team_environment.md), [протокол v1 для согласования](measurement_protocol_v1.md). До синка не реализуем runner и не запускаем новые GPU-эксперименты. После обсуждения — самостоятельное парное сравнение, интеграция с автоподбором позже.

## Основание

[Презентация проекта](https://docs.google.com/presentation/d/1JPnSHGIRyOra7IJYShzRCHom0oOhQm8i/edit), повторно прочитана 29 октября через текстовый экспорт:

- Слайды 9–10: У1 отвечает за общий протокол скорости, потребления и качества, среду и сиды. У2 — данные и квантование; У3 — автоподбор; У4 — CLI и архитектура. Протокол нужен этапам 3 и 4; готовый CLI не является его входным условием.
- Слайд 11: результат У1 — протокол v1, измерительный пайплайн и FP-baseline всех моделей с таблицей p95/памяти. Даты 28 октября и 3 ноября — исходный график презентации, не заново согласованные сроки. На 29 октября общий пайплайн ещё не готов.
- Слайд 12: одна GPU-конфигурация, записанные версии/драйвер/CUDA, сиды и детерминизм, lock или контейнер; один скрипт и формат результатов; p50/p95 после прогрева, повторы и интервал; пиковая память и размер модели; in-domain/OOD/хвосты отдельно и совпадение вердиктов.
- Слайды 4 и 8: основной backend семестра — ONNX Runtime; цель проекта — не менее 20% снижения p95 и проверка отсутствия деградации на хвостах. Наш прежний screening-порог 10% по p50 — внутренний фильтр, не выполнение этой цели. FLA/compile остаются полезными контролями и исследовательскими результатами, не автоматическим изменением scope CLI.

Параметры записаны в [team_base.json](../env/team_base.json), прямые версии — [team_base.constraints.txt](../env/team_base.constraints.txt). Constraints не являются полным lock и сами ничего не устанавливают. Выбранная площадка — Kaggle по README Koala; одна T4 `cuda:0`, batch 1, concurrency 1, два CPU-потока. Версии host-драйвера/CPU/RAM — наблюдавшиеся значения, не обещание новой VM. Различия заносятся в паспорт; среда не подменяется молча.

Обновление 29 октября: сохранены наши ORT 1.23.2 / GLiNER2 2.1.0 / FLA 0.4.2. [Smoke 45555111 прошёл на T4](team_environment_smoke.md): установка, CUDA/ORT MatMul, GLiNER eager/ORT и HaloGuard FP32/FP16/FLA. Совместимость подтверждена в границах трёх синтетических входов и повтора; скорости, качество и все модели команды не проверялись.

Важные пробелы:

- Совместная работа ORT с явно установленными CUDA 12 библиотеками и PyTorch cu130 прошла в одном worker на GLiNER. Разрешённые CPU-операции — служебные по `metadata-cpu-v1`, граф не CUDA-only.
- GLiNER и FLA проверены с Transformers 5.20.1, Halo использует отдельный новый адаптер. Compile и остальные модели команды ещё не проверены; специальные пакеты не становятся обязательными импортами общего runner.
- Workaround NVRTC из Koala воспроизведён: `libnvrtc-builtins.so.13.0`, пакет `nvidia-cuda-nvrtc==13.0.88`. Это часть установки, не заявленное ускорение.
- Установка в свежий venv и её reports/freeze есть в 45555111; полный lock из 96 wheels оформлен и сверен с workers. Повторное развёртывание именно из lock ещё не выполнено, контейнера нет. Предупреждение host sitecustomize об отсутствии wrapt осталось, хотя все проверки прошли; его происхождение ещё нужно установить.

## Параметры протокола

Ниже предложение У1 на основе уже проверенной методики, а не утверждение, что все коллеги использовали эти настройки.

- Seed модели 42; порядок нагрузок 17/42/123. `eval`, `inference_mode`, TF32 выключен, cuDNN benchmark выключен; deterministic algorithms `warn_only`, предупреждения сохраняются. Это не обещание битовой идентичности.
- Основной тайминг: текст → scores/вердикт на CPU, с синхронизацией GPU; загрузка, экспорт, compile, логирование и profiler вне latency. Forward/encoder-only — отдельные вспомогательные поля. Не заменять авторский scoring генерацией одной метки.
- Прежний screening: 20 прогревов, A/A 2×30 и A/B 3×100, чередование AB/BA и одинаковые входы внутри пары. Полный confirmation — 5×100 и независимые сессии; не обязательный повтор всех экспериментов сейчас.
- Сохранять raw latency, p50/p95 и блочные интервалы обоих показателей, дрейф и A/A, длительность подготовки, температуры/частоты и ошибки. Не удалять неудобные прогоны; тысячи запросов одной VM не считать независимыми VM.
- Пиковая память всего GPU-процесса — отдельно от Torch allocated/reserved. Для ORT нельзя сравнивать только Torch counters. Частота опроса и то, что sampled peak может пропустить короткий пик, должны быть видны в отчёте. Размер модели: логические bytes параметров/буферов и размер экспортированного артефакта, с единицами и без смешивания с VRAM.
- Качество: baseline/candidate на одном размеченном наборе, по in-domain/OOD/хвостам отдельно; FPR/FNR, размеры срезов, изменения меток/оценок и неопределённость. У2/куратор задают данные, смысл меток и допустимую деградацию. Без них `quality_evaluated=false`; совпадение вердиктов на синтетике не заменяет quality gate.

## Очередь работ и приёмка

| Шаг | Что делаем | Проверка готовности |
| --- | --- | --- |
| 0. Точка отсчёта — сделано | Выбираем опубликованную базу, фиксируем параметры, источники и различия | JSON и constraints согласованы с TARGET Koala; ссылки привязаны к commit; неизвестные зависимости не названы проверенными |
| 1. Среда — smoke пройден, lock оформлен | 96 wheels с SHA256, инструкция отдельного venv и проверка inventory; provenance исходного запуска сохранён | Сверка всех workers пройдена. Повторное развёртывание из lock и причина host sitecustomize warning ещё не проверены; большой benchmark не нужен |
| 2. Общий протокол v1 — предложение готово | Спецификация скорости, памяти, размера модели, качества и результата; обсуждаем на синке | Определены границы времени, пары/A-A, память и quality-report; требования и данные качества не выдуманы. Принятие командой ещё впереди |
| 3. Измерительный runner | Один запускаемый скрипт для моделей/конфигураций; сначала один encoder и один decoder | Из чистого процесса выдаёт один формат результатов, raw timings и частичный результат при ошибке; CPU-тесты статистики/пар/статусов плюс короткие GPU smoke. Это инструмент У1, не пользовательский CLI У4 |
| 4. Таблица baseline FP | Через общий runner владельцы моделей снимают исходные конфигурации | Для каждой модели явный dtype и scoring, p50/p95/память/размер; единые источники входов и protocol/runtime IDs. Отсутствующая модель помечена, чужие старые CSV не объявлены новым общим baseline |
| 5. Передача У2/У3 | Общий измеритель для INT8 и поиска настроек, описание чтения результата | Они могут запустить свою конфигурацию и получить сопоставимый отчёт без копирования нашего ноутбука; quality gate подключается по данным У2. CLI интегрируем позже |

Ближайший шаг — обсуждение подготовленного комплекта, затем реализация самостоятельного измерителя и baseline-таблицы. Повтор FLA/compile/ONNX confirmation, новые оптимизации, маршрутизация по длине и универсальный CLI не входят в комплект к синку. Маленький smoke-test проверяет среду, а не заново доказывает ускорение.

## Что уже можно переиспользовать

[Опубликованные результаты и трейсы](https://github.com/kekwak/HiveTrace-AutoTune-Guardrails/tree/cec4f5eb2b212b8c03df6ca005be81710837fcff) дают испытанные части: парный тайминг, A/A, численную регрессию, metadata и архивирование ошибок. Это строительные блоки, не готовый общий протокол: ещё нужны runtime-независимая память, размер модели, единый quality-report и модельно-независимый запуск. Не меняем исторический пакет, чтобы сохранить происхождение результатов.
