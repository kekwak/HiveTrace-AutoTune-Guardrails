# CLI: команды за минуту

Основной путь: **plan -> eval -> report**. Исполнение модели: **run / serve**.
[Установка, данные и готовые конфиги](u1_handoff.md#общий-cli-plan--eval--report)
находятся в единственной операционной инструкции; ниже только назначение команд.

## Основные команды

| Команда | Что делает | Загружает модель / использует GPU |
|---|---|---|
| `inspect MODEL` | Читает архитектуру и metadata HF/local checkpoint | Нет |
| `plan --config BASE.json --output PLAN.json` | Предлагает один кандидат по capabilities и сохраняет полный baseline/candidate-контракт | Нет |
| `eval --config PLAN.json --output RUN` | Измеряет baseline, затем кандидат штатным протоколом У1 | Да, последовательно |
| `eval ... --baseline-ref BASELINE` | Измеряет только кандидата относительно полного совместимого baseline, каталог или ZIP | Только candidate |
| `report RUN` | Пересобирает отчёт из каталога или ZIP: статус, p95/p50, эффект, память, ответы | Нет, offline |
| `run --config PLAN.json --text "..."` | Выполняет один запрос выбранным вариантом; можно повторять `--text` | Да |
| `serve --config PLAN.json --port 8000` | Держит один вариант в памяти; HTTP `POST /infer` на localhost | Да |

`run/serve` по умолчанию выбирают candidate; `--variant baseline` явно выбирает
baseline. Никакого reference-прогона на каждом запросе. `--messages FILE.json`
у `run` принимает одну переписку. HTTP принимает `{"inputs":["..."]}` или
`{"messages":[{"role":"user","content":"..."}]}`.

`plan MODEL` без `--config` — прежний metadata-only путь, не полный план У1.
Непроверенный план не обещает ускорения. `run` не заменяет `eval`.
Каждому запуску задавайте новый output: существующие результаты не перезаписываются.

## Что читать в report

- `cells`: отдельная строка на бакет и batch size. p95 — время **всего батча**,
  от сообщений до scores/вердиктов на CPU, не только forward.
- `p95.ratio = candidate / baseline`. Коэффициент ускорения: `1 / ratio`.
  Снижение задержки: `100 * (1 - ratio)%`; эти две величины не взаимозаменяемы.
- `reference_pass`: полный search прошёл порог, проверки наблюдаемого шума
  и согласованности ответов. Сравнение непарное, не независимая репликация.
- `below_target`: убедительный эффект ниже требования либо устойчивое замедление.
  `inconclusive`: выводу мешает шум/направление эффекта; `incomplete`: не все стадии готовы.
- `quality_evaluated=false`: размеченный набор не оценивался. Ноль flips не доказывает safety.

Для демонстрации скорости достаточно показать p95-speedup каждой ячейки и статус.
Это фильтр представления готового отчёта, не сокращённый измерительный протокол.
Инженерный порог: снижение p95 строго >20%; параметрический: >10%.
Случайные ускорения, не прошедшие шумовые проверки, не называются успехом.

## Остальные команды

| Команда | Назначение |
|---|---|
| `datasets` | Проверяет загрузку quality/performance источников прежних режимов |
| `benchmark` | Прежнее сравнение Transformers/ORT для sequence classification |
| `optimize` | Прежний подбор конфигурации; сохраняет `execution.json` и выбранный артефакт для `run/serve` |
| `tune-model` | Отдельная проверка text-to-logits forward и compile |
| `check-generation` | Отдельное сравнение greedy generation с KV cache и без него |
| `compare-app` | Сравнивает два внешних приложения по JSONL-контракту |

Эти команды не подменяют критерии У1: например, исторический `optimize` использует
свой p99-критерий. [Подробные флаги и примеры](cli-guide.md).

Низкоуровневый `tools/benchmark.py` остаётся доступен: `setup`, `auth-check`,
`fetch-data`, `prepare-data`, `plan`, `preflight`, `run`, `quality`, `report`, `table`.
Он нужен для среды, новых данных, baseline-only/явного confirm, отдельного quality
и общей таблицы. Для командного демо используйте общий CLI выше, не другой runner.

Подсказка по любой команде: `guardrail-tuner COMMAND --help`.
