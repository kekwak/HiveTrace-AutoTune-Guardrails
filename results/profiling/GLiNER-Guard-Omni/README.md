# GLiNER Guard Omni: поиск узких мест и проверка гипотез

Подготовлено 1 ноября 2026. Основной профиль — исторический прогон
`20261026T093634Z_9fcd4434`; сравнение runtime — опубликованный эксперимент
28 октября. Это программный разбор сохранённых материалов, без новых GPU-запусков.

## Краткий вывод

На коротких входах разумным первым направлением оказались накладные расходы
исполнения DeBERTa encoder; на длинных заметнее затраты attention и операций
относительных позиций. Compile уменьшает число GPU-запусков и полный latency,
особенно на коротких входах. ONNX затем улучшил short/medium относительно compile,
но не оказался универсально быстрее на long и по смешанному p95.

Проекции относительных позиций — отдельный наблюдаемый источник работы и кандидат
для предвычисления. Из этих профилей **не следует**, что compile или ONNX уже
закешировали эти проекции, либо что их ручное кеширование даст измеренный выигрыш.

## Условия и границы

- Checkpoint: `hivetrace/gliner-guard-omni`, revision
  `763f8aa9a7714dd2c3264f3751acdd5d854c5ac4`; GLiNER2 с DeBERTa encoder.
- Kaggle, одна T4, FP32, batch 1. Python 3.13.15, PyTorch 2.11.0+cu128;
  точные зависимости и паспорт: [environment.json][environment].
- Контроль `B0`: eager. Кандидат `C1_dynamic`: только encoder,
  `torch.compile(mode="default", dynamic=True, fullgraph=True)`.
  Схема `safety`, argmax, голова и полный `extract()` сохраняются.
- Основная latency — текст/схема → готовый ответ `extract()`. Encoder-only на
  готовых GPU-тензорах — отдельный диагностический показатель, не полный запрос.
- Legacy short/medium/long: 31/128/383 пользовательских и 47/144/399 полных
  токенов. Длины проверены по сырым latency-строкам; это не новый модельный отбор.
- Пять A/B-пар по 100 запросов, семь сценариев, A/A отдельно; профили short/long
  по три итерации вне latency. В этой серии выполнена одна подтверждающая сессия.

## Что видно в baseline-профиле

Время ниже — сумма длительностей kernels компонента, делённая на три итерации,
а не wall time запроса. `Encoder, остаток` — категория атрибуции для операций,
не попавших в более конкретные группы; её нельзя складывать с общей длительностью
области encoder как с независимым слоем. Fused operators оставлены составными.

| Компонент B0 | Short, мс/итерацию | Long, мс/итерацию |
| --- | ---: | ---: |
| Encoder, остаток | 3,43 | 15,63 |
| Проекции относительных позиций | 3,12 | 4,19 |
| Операции относительных позиций | 1,10 | 9,60 |
| Relative attention | 0,97 | 8,55 |
| Проекции query/key входа | 0,91 | 4,03 |
| Классификационная голова | 0,035 | 0,040 |

1. В baseline наблюдаются **72 kernels проекций относительных позиций за три
   итерации**, то есть 24 на запрос. Атрибуция указывает на query/key-проекции
   relative-position ветви в 12 слоях. Это не padding пользовательского текста
   до размера таблицы позиций. Гипотеза предвычисления требует отдельной проверки.
2. При длинном входе растёт стоимость relative-position/attention операций.
   Поэтому сокращение накладных расходов не обязано давать одинаковый процент
   выигрыша на коротких и длинных запросах.
3. GPU-kernels классификационной головы малы относительно encoder. Это не означает,
   что вся CPU-подготовка и постобработка бесплатны; для решения используется
   полный `extract()`, не только ускоренный encoder-forward.
4. Сумма kernel-времени короткого baseline существенно меньше обычного полного
   latency. Это диагностический признак для проверки overhead, **не вычисление
   CPU-доли вычитанием величин из разных измерений** и не доказательство GPU idle.

## Почему выбрали compile

| Профиль | Все kernels за 3 итерации | Составные fused kernels за 3 итерации |
| --- | ---: | ---: |
| B0 short | 2 343 | 6 |
| C1_dynamic short | 1 049 | 366 |
| B0 long | 2 199 | 6 |
| C1_dynamic long | 869 | 366 |

В compiled trace присутствуют составные Triton operators, объединяющие softmax,
gather, преобразования, нормализацию и другие операции. Уменьшение числа запусков
и появление fusion согласуются с гипотезой overhead. Точное распределение времени
внутри fused kernel неизвестно: слово `copy` в имени не делает весь kernel копированием.
Compiled trace сохраняет границу encoder, но детализация отдельных модулей теряется;
отсутствие отдельной строки relative_projection не доказывает устранение вычисления.

Полные агрегаты и хеши: [evidence.json](evidence.json). Неизвестные события сохранены.
Реальный speedup проверяется вне профайлера, а не по одному уменьшению числа kernels.

## Проверка обычной latency

Медианы пяти блочных p50/p95 полного `extract()`, миллисекунды, прогон 26 октября.
Не pooled-квантили; абсолютные числа относятся только к этому запуску.

| Сценарий | p50 eager → compile | p95 eager → compile |
| --- | ---: | ---: |
| legacy_short | 45,62 → 17,58 | 49,30 → 18,46 |
| legacy_medium | 46,36 → 21,21 | 48,57 → 23,48 |
| legacy_long | 57,01 → 51,20 | 58,91 → 54,42 |

В той же серии `varying_long` остался inconclusive: эффект не превосходил дрейф
контроля. Нельзя выбрать только удачные строки и объявить подтверждение всех длин.
На 300 отложенных синтетических примерах смен вердиктов не было, max Δp_unsafe
0,000002921; это не оценка safety-качества. [Сценарии, шум и отношения][latency].

## Почему проверили ONNX и что это добавило

Готовый runtime — следующий способ проверить более эффективное исполнение графа,
не переписывая саму модель. Вариант `G1_service` заменяет encoder на ORT CUDA с
IOBinding; голова и остальной `extract()` остаются в общем пути. Допускаются только
проверенные служебные CPU-операции над метаданными; произвольный CPU fallback запрещён.
Факт применения конкретного fusion следует проверять по графу/trace, а не названию ORT.

28 октября выполнено прямое парное сравнение ONNX–compile в одной T4-сессии.
Ниже медианы трёх блочных квантилей; это **другая серия**, не продолжение таблицы выше.

| Сценарий | p50 compile → ONNX, мс | p95 compile → ONNX, мс | Интерпретация |
| --- | ---: | ---: | --- |
| varying_short | 18,08 → 9,83 | 19,23 → 10,59 | Перспективный выигрыш в этой сессии |
| varying_medium | 19,32 → 16,41 | 20,51 → 17,56 | Перспективный выигрыш в этой сессии |
| varying_long | 46,05 → 49,80 | 48,89 → 51,99 | ONNX наблюдаемо медленнее; исходный статус inconclusive |
| mixed | 21,73 → 17,78 | 46,54 → 50,33 | Улучшение p50 не компенсирует ухудшение p95 |

Вывод: проверять runtime **по длинам и целевой метрике**, не назначать одного
универсального победителя. Точка переключения и гибридная маршрутизация не проверены.
Обе реализации прошли численную регрессию на 300 development-примерах без flips;
близких к порогу примеров не было. [Полный отчёт прямого сравнения][comparison].

## Карта гипотез и оставшиеся ограничения

| Наблюдение | Кандидат | Статус |
| --- | --- | --- |
| Много отдельных операций encoder, большой выигрыш на коротких входах | Compile encoder | Проверен на историческом T4-стеке; не универсальное ускорение всех будущих сред |
| Готовый runtime может иначе выполнять тот же граф | ORT CUDA + IOBinding | Проверен; эффект относительно compile зависит от длины |
| Повторные проекции относительных позиций | Предвычисление в eval при неизменных весах | Отдельный измеренный эффект не установлен; нужна инвалидация при dtype/device/весах/train-eval |
| На длинных входах растут матричные и attention-операции | Другой dtype/backend | Не выводить эффект из FP32 compile/ORT; нужна отдельная регрессия и сравнение |

Память PyTorch не включает весь ORT runtime. Экспорт/компиляция и прогрев исключены
из latency; из этих таблиц нельзя вывести окупаемость подготовки или точный GPU peak.
Аппаратных счётчиков для compute/memory-bound диагноза нет. SM utilization не измерена.
Качество на разметке и перенос на новый корпус/RTX 4090/5090 здесь не проверялись.
