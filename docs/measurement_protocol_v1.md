# Протокол измерений У1 v1

Актуально на **9 ноября 2026** для реализованного измерителя, конфигураций
`schema_version: 3` и ролевого корпуса v4. Это спецификация текущего поведения,
а не обещание GPU-совместимости RTX или сохранения safety-качества.
[Запуск и подключение конфигураций](u1_handoff.md), [готовность](u1_handoff_readiness.md),
[план У1](u1_protocol_plan.md).

Основание: [задание, слайды 8–12](https://docs.google.com/presentation/d/1JPnSHGIRyOra7IJYShzRCHom0oOhQm8i/edit)
и последующие согласования по бакетам, нативным входам и разделению инженерных,
параметрических и квантованных конфигураций. Исторический [v0.1](measurement_protocol.md)
не меняется; [предложение от 29 октября](https://github.com/kekwak/HiveTrace-AutoTune-Guardrails/blob/23a4874a183f0815e22e4b33b785d13c16e5c7be/docs/measurement_protocol_v1.md)
с семью сценариями не является текущим протоколом.

## 1. Среда и контракт

- Целевая среда: Linux x86_64, Python 3.13, профиль `team-rtx`, одна RTX 4090 либо
  RTX 5090 на GPU 0. Результаты 4090, 5090 и исторической T4 группируются раздельно.
  Восемь baseline-адаптеров прошли [smoke на T4](../results/u1_handoff/2026-11-04-review-smoke/validation.json);
  отдельный [smoke Laya на RTX 4090](../results/u1_handoff/2026-11-08-laya-rtx4090/validation.json)
  подтвердил нативный BF16 autocast. Проверку остальных моделей и RTX 5090
  выполняют владельцы; smoke не заменяет полный baseline.
- Используется [97-wheel lock](../env/team_rtx.lock.json) без автоматической смены
  версий: PyTorch CUDA 13 и отдельные CUDA 12 библиотеки ORT. Сохраняются версии,
  драйвер/CUDA/cuDNN, GPU, исходники, dtype, фактический backend и доступная telemetry.
- Без `batch_sizes_by_bucket` используется прежний batch 1; с полем запускается
  статическая сетка ниже. Concurrency 1; одновременно на GPU только один вариант. Каждая сторона,
  повтор памяти и профиль исполняются в отдельном свежем worker-процессе.
  Лимит всего запуска — 10 часов; новая VM для каждого worker не требуется.
- Model seed 42, seed порядка 17 по умолчанию; допустимы 42/123. Два CPU-потока,
  `eval`, `inference_mode`, TF32 off, cuDNN benchmark off,
  deterministic algorithms `warn_only`. Это не обещание битовой идентичности.
- Baseline — eager/штатный SDK в [закреплённом режиме](baseline_modes.md).
  Checkpoint/tokenizer revisions, prompt/schema, native labels, scoring, tie/stop rules
  фиксируются [контрактом](../u1_benchmark/contracts.py).
  OpenGuardrails: веса/tokenizer 0124 + task-шаблон 2510, не родной шаблон 0124.
- Laya сохраняет нативную precision SDK без выбора dtype по названию GPU.
  `metadata.precision` фиксирует dtype параметров и режим autocast; он одинаков во
  всех workers одного варианта. В инженерной паре вычислительная precision также
  одинакова; параметрическое и квантованное сравнения могут явно отличаться.
  CPU fallback, отключение AMP и дрейф режима останавливают worker, включая quality.
  Данные валидируются по контракту подготовки без вычислительных `rules`; полный
  inference-контракт workers проверяется строго. Старые архивы без паспорта precision
  обозначаются `historical_unrecorded` и не подтверждают эту новую политику.
- Кандидат сохраняет входы и смысл задачи. Весовой артефакт, precision и runtime
  квантования меняются явно. Нет скрытой усечки, CPU-offload или подмены backend;
  для ORT разрешены только доказанные служебные CPU-узлы `metadata-cpu-v1`.

## 2. Общий корпус и модельные бакеты

Один исходный пул сообщений EN/RU: user-only, assistant-only и user+assistant.
Модель использует свой нативный формат и применимые роли; [матрица входов](u1_handoff.md#входы-моделей)
определяет оцениваемое сообщение и контекст. Неприменимые форматы не переименовываются.

| Бакет | Полная длина, включая шаблон и специальные токены | Обязательные модели |
| --- | --- | --- |
| B1 | 1–512 | Все восемь |
| B2 | 513–1024 | HaloGuard, HiveTraceGuard-Pro, OpenGuardrails, ShieldGemma |
| B3 | 1025–2048 | Те же четыре decoder-модели |
| B4 | 2049–4096 | Те же четыре decoder-модели |

На модельный бакет отбираются **400 уникальных эффективных входов**, суммарно по
применимым форматам. Бакеты разных моделей могут содержать разные ID; один ID может
иметь разные бакеты. Это не пересечение длин всех моделей. Отбор стремится к широкому
покрытию восьми интервалов длины; пробелы видны в отчёте, padding для их заполнения нет.

Внутри baseline/candidate-пары обязательны одинаковые ID, исходные сообщения,
подготовленные token IDs/маски и порядок. Кандидат не пересобирает бакеты.
Индексы проверяются через реальный путь подготовки. Нехватка входов или устаревший
контракт блокируют screening. Корпус не размечен и не представляет production-трафик.

## 3. Граница времени и одиночный протокол

Основной тайминг: синхронизация GPU → старт → нативная подготовка из сообщений,
токенизация, передача на GPU, вычисления, scores/вердикт на CPU → синхронизация → стоп.
Подготовка входа остаётся внутри таймера; готовые тензоры и ответы не подставляются
вместо повторной обработки. Для GLiNER измеряется полный `extract()`, не encoder-only.

Загрузка, экспорт, компиляция, подготовка форм, backend proof, прогрев, логирование
и профайлер учитываются отдельно. Новая компиляция внутри latency-серии делает её
непригодной для вывода об ускорении. Прогреваются формы текущего worker, не весь корпус
перед каждой короткой серией.

| Режим | Состав на обязательный бакет | Интерпретация |
| --- | --- | --- |
| Preflight | Весь выбранный корпус, входы, конечность, A→B→A, лимит/превышение и backend | Проверка контракта, без latency-серий |
| Smoke | Два входа на бакет, границы, A→B→A, CUDA proof и память | Совместимость, не baseline |
| Pilot | Полный preflight, A/A две пары ×30, одна A/B-пара ×12 | Проверка пути запуска, без pass ускорения |
| Baseline-only | Preflight, A/A две пары ×30, три серии ×400 одного baseline | Полный исходный результат, без фиктивного кандидата |
| Comparison | Preflight обоих вариантов, A/A две пары ×30, A/B три пары ×400 | Screening конкретного кандидата |

В каждой A/A-паре обе стороны — baseline; числа запросов указаны **на сторону**.
Перед каждой latency-стороной — 20 прогревов. Порядок сторон AB/BA чередуется;
внутри пары ID и порядок одинаковы. Для baseline-only выполняется одна сторона
каждой из трёх основных серий. Smoke ограничен часом на модель; pilot не включает
полные memory/profile-стадии. В полном режиме они обязательны.

### Статические батчи

Поле `batch_sizes_by_bucket` включает отдельный протокол результатов
`batch_protocol_version: 1`, не меняя версию корпуса. Старые конфигурации без
поля продолжают выполнять одиночный протокол выше. **Сетка предварительная, batch
sizes не финальные.** На RTX 5090 прошли baseline-smoke четырёх encoder (20/20)
и HaloGuard (11/11); остальные decoder и batch-оптимизации требуют проверки.
[Результаты и ограничения](u1_handoff_readiness.md#статус-публикации-10-ноября-2026).
Smoke не определяет максимальную вместимость и не подтверждает ускорение.

| Класс | Бакет | Batch sizes |
| --- | --- | --- |
| Encoder | B1 | 1, 8, 16, 32, 64 |
| Decoder | B1 | 1, 4, 8, 16, 32 |
| Decoder | B2 | 1, 4, 8 |
| Decoder | B3 | 1, 4 |
| Decoder | B4 | 1 |

Бакет определяется длиной **до padding**. Внутри него фиксированная случайная
перестановка, без сортировки по длине; обе стороны используют одинаковые батчи.
Padding только до наиболее длинного нативного входа батча, без усечки и без
фиктивных примеров. В одном батче ID не повторяются. Сохраняются ID, порядковые
номера повторений, длины, хеши входов и планов. Native SDK вправе выполнять
последовательные операции головы, но общий encoder должен получать батч:
цикл независимых одиночных запросов не является batch backend.

В основной серии `max(400, 100 * batch_size)` обработок. Перестановка повторяется
целиком: для batch 64 это 6400 обработок, 100 батчей и 16 появлений каждого из
400 ID. Количество независимых примеров от повторов не увеличивается.

| Режим | Состав на объявленную ячейку (бакет, batch size) |
| --- | --- |
| Preflight / smoke | Полные короткий, длинный и смешанный батчи; A-B-A, точная граница и превышение, backend proof; без pass ускорения |
| Pilot | 20 прогревов, одна A/B-пара по 12 полных батчей; baseline-only одна серия; без A/A, полных memory/profile и pass |
| Screening | 20 прогревов перед стороной, A/A 2 пары по 30 батчей, A/B 3 пары основного объёма; baseline-only 3 серии и A/A |

Положительная граничная проба использует верх текущего бакета, не глобальный лимит
decoder: B1 при batch 32 проверяется на 512, а не на 4096 токенах. Превышение общего
лимита модели проверяется отдельно на отказ до forward, без вычисления длинного батча.

Короткая диагностика проводится перед матрицей, не перед каждой измеряемой стороной.
Её результат связан с исходниками, конфигурацией, данными, runtime и precision.
В свежих compile/ORT workers подготовка необходимых форм всё равно выполняется
вне таймера. Profiler proof и дополнительные диагностические проходы не повторяются
в latency workers. Полный основной таймер принимает сообщения, а не кеш тензоров.

Основной p95 относится ко **всему батчу**; `latency / batch_size` не является
задержкой пользовательского запроса. Throughput = число обработанных текстов /
сумма измеренных времён батчей. Указываются полезные позиции, все padded-позиции,
добавленные pad-токены и их доля. Нет моделирования очереди или времени набора батча.

Приёмка и шум оцениваются по каждой объявленной ячейке; необъявленные сочетания
имеют статус `not_scheduled`. Отметка «ускорение во всей сетке» требует положительного
эффекта с пройденными шумовыми проверками во всех объявленных ячейках, но не означает
достижения порога 20%/10%, отсутствия flips или сохранения качества. Эти статусы
отдельны. OOM/unsupported не уменьшают батч автоматически: ошибка сохраняется,
оставшиеся ячейки запускаются в свежих процессах в пределах общего лимита 10 часов.

Вердикты агрегируются по уникальным ID внутри ячейки, без примешивания одиночного
preflight. Single-to-batch диагностика использует уже измеренные ответы batch 1
и больших размеров, без дополнительного прогона. При отсутствии batch 1 она недоступна.
Для генерации `generated_tokens` включает собственный сгенерированный EOS, но не
padding после завершения ответа, даже если pad и EOS имеют одинаковый ID.

Memory: 3 свежих процесса на вариант и ячейку; минимальное число полных проходов
корпуса, кратное batch size, без хвостов. Short/long profiles также отдельные.
Quality запускается отдельно с `quality_batch_sizes` (по умолчанию `[1]`),
без переноса скоростных бакетов. Каждый размер проходит тот же размеченный набор,
включая неполный хвост; результаты, покрытие и ошибки показываются отдельно.
Baseline/candidate сравниваются при одинаковом размере и составе батчей.
Single-to-batch изменения доступны только при явно запрошенном batch 1.
Новый quality-путь требует собственной GPU-проверки; speed-smoke её не заменяет.

## 4. p95, шум и приёмка

Главный показатель — **pooled p95 внутри бакета**, p50 дополнительный.
Снижение = `1 − p95_candidate / p95_baseline`; speedup = обратное отношение задержек.
Квантили используют линейную интерполяцию. 95%-интервал отношения строится по целым
парным блокам: 2000 bootstrap-повторов, seed 42, без независимого ресэмплинга запросов.

[Реализованные проверки](../u1_benchmark/statistics.py):
- Эффект должен превышать A/A envelope и дрейф p95 baseline между A/B-блоками.
  A/A envelope = `max(max(r, 1/r) − 1)` по отношениям p95 сторон A/A;
  дрейф = `max(p95 блока) / min(p95 блока) − 1`.
- Во всех трёх A/B-блоках направление должно быть положительным; верхняя граница
  интервала candidate/baseline — ниже 1. Неполнота не превращается в pass,
  шум или смешанное направление дают `inconclusive`.
- Инженерный кандидат: снижение pooled p95 **строго >20% в каждом обязательном
  бакете**; параметрический — **строго >10%**. Дополнительно ноль изменений
  native verdict и ноль нестабильных повторов. Провал одного бакета запрещает pass.
- Устойчивое замедление, превышающее A/A и дрейф, — отрицательный результат
  `below_target` / итог `rejected`, а не повод повторять до удобного процента.

Baseline-only показывает p95 каждой серии, A/A-отношения, симметричный разброс,
дрейф и блочные интервалы pooled p50/p95. Новый порог стабильности не вводится:
`baseline_complete` означает комплектность при стабильных вердиктах, не отсутствие
latency-шума; нестабильность вердиктов даёт `baseline_unstable`.
Три серии одной VM дают ограниченную оценку неопределённости, не независимое подтверждение.

Для квантования показываются скорость, изменённые уникальные ID, направления,
нестабильность и макросреднее долей изменений по обязательным бакетам.
Повторы ID не увеличивают знаменатель. Ненулевые flips не вызывают lossless-отказа;
`quantization_measured` не означает принятие без согласованного quality-правила.

## 5. Память, размер и профили

Полный запуск включает три memory-повтора на вариант, каждый в свежем процессе,
и short/long-профили вне latency. После прогрева полный применимый корпус проходит
в отдельном inference-окне. Setup peak и inference peak не смешиваются.

GPU-память процесса опрашивается примерно каждые 50 мс, с фактическими интервалами
и PID; короткий пик может быть пропущен. Torch allocated/reserved указываются отдельно:
для ORT они не равны всей памяти процесса. Сброс Torch peak counters не освобождает
память; `empty_cache` между прогревом и inference не вызывается.

Размер уникальных параметров/буферов и файлов checkpoint/экспорта — отдельно от VRAM.
Учитываются ONNX external data и остающаяся копия encoder. Трейсы содержат реальные
GPU kernels; fused operators не разбиваются на copy/norm по подстроке имени.
Профайлер и его overhead не входят в обычную latency.

## 6. Вердикты, качество и результат

Численная согласованность: native verdict, именованные scores при наличии,
направления изменений и устойчивость повторов. Девять классов Koala не превращаются
автоматически в safe/unsafe; отсутствующие вероятности не выдумываются.

Quality-набор подключается отдельно: target, объект разметки user/assistant,
явный mapping native labels и именованные срезы. Нельзя сопоставлять метку ответа
с оценкой запроса HaloGuard. Неприменимые режимы, over-limit и ошибки остаются в coverage.
Считаются confusion matrix, accuracy, macro-F1; для явной бинарной задачи — FPR/FNR,
с N и неопределёнными знаменателями `null`. Статистического gate сохранения качества
пока нет; интервалы для quality-метрик текущий отчёт не строит.

У2 предоставляет данные и вместе с командой/куратором согласует правило качества,
включая in-domain/OOD и хвосты: языки, код, обфускации. До реального набора
`quality_evaluated=false`; совпадение вердиктов на speed-корпусе не доказывает safety.
Исходная цель задания — отсутствие деградации на хвостах. Ненулевой допуск не
предполагается автоматически: это отдельное согласование изменения требования.

Результат хранит config/contract/source hashes, manifest и входные индексы, raw latency,
p50/p95 и интервалы, пары/шум/дрейф, setup/warmup, память/размер, backend/traces,
quality либо её отсутствие, ошибки и частичные стадии. Закрытые тексты и промпты
по умолчанию не архивируются. Offline report/table сохраняют разные группы среды
и корпуса раздельно; smoke в baseline-таблицу не включается.
