## Что входит

| Конфигурация | Baseline | Кандидат | Бакеты |
| --- | --- | --- | --- |
| `halo_fla` | FP16 eager, reference linear attention | FP16, только FLA linear attention | B1–B4 |
| `gliner_compile` | FP32 eager, полный extract | FP32 encoder compile, default/dynamic/fullgraph | B1 |
| `gliner_ort` | FP32 eager, полный extract | FP32 encoder ORT CUDA + IOBinding | B1 |

ORT допускает только доказанные служебные CPU-операции `metadata-cpu-v1`; это не CUDA-only граф.
Полный extract включает голову и подготовку. Сохранённая копия encoder явно учитывается в памяти.
У HaloGuard prompt, thinking off, `Safety: `, threshold 0.65 и один forward неизменны.
GLiNER: safety, argmax, tie → safe. FP32-режим Halo не является скрытым более медленным
знаменателем сравнения: оба варианта здесь FP16. Отдельной FP32-регрессии этот комплект не заявляет.

## Подготовка

На пользовательской Linux x86_64 машине с T4 и Python 3.13 открыть корень этого клона.
На Kaggle включить Internet и выбрать T4. Скрипт работает из терминала/обычного shell;
ноутбук не требуется. Если площадка предоставляет только notebook-интерфейс, в ячейке
можно вызвать ту же команду, но логика измерений остаётся в скрипте.

```bash
python3.13 tools/benchmark.py setup --environment .u1-env
```

Устанавливаются точные 96 wheels из существующего lock, в `.u1-env/venv`, без изменения host PyTorch.
Основной Python и host pip не обновляются. CUDA 13 PyTorch и CUDA 12 библиотеки ORT сохраняются.
Команда проверяет inventory и CUDA primitive; это не проверка всех моделей или скоростей.
Отсутствие Linux/Python 3.13/T4, расхождение lock или CUDA останавливают выполнение.
Предупреждения startup/sitecustomize сохраняются в логах, механизмы startup автоматически не отключаются.

Каталог setup должен быть новым. При неудачной установке сохранить его для диагностики,
исправить причину и использовать новое имя каталога. Успешную среду повторно устанавливать
перед каждым сравнением не нужно. Каждый worker повторно проверяет inventory и CUDA.

## Приёмка: preflight → pilot → screening

Пример для HaloGuard:

```bash
python3.13 tools/benchmark.py preflight \
  --config configs/benchmark/halo_fla.json --environment .u1-env \
  --output benchmark_runs/halo-preflight

python3.13 tools/benchmark.py run --pilot \
  --config configs/benchmark/halo_fla.json --environment .u1-env \
  --output benchmark_runs/halo-pilot

python3.13 tools/benchmark.py run \
  --config configs/benchmark/halo_fla.json --environment .u1-env \
  --output benchmark_runs/halo-screening
```

Для GLiNER выполнить такой же порядок с `configs/benchmark/gliner_compile.json`
и `configs/benchmark/gliner_ort.json`, задавая отдельные выходные каталоги.
Нельзя запускать сравнения параллельно на одной GPU. Новая VM между этими тремя сравнениями
не обязательна; baseline внутри каждого сравнения измеряется заново.

`preflight` проверяет полный корпус и оба варианта, численные ответы, A→B→A,
фактические входы модели и точные execution-границы: 512 для GLiNER, 4096 для HaloGuard.
Запрос на один токен длиннее должен отклоняться до вычисления модели. Пограничные строки
создаются отдельно из повторяющегося простого токена: это диагностика лимита, не добавка к датасету скорости.
Итог — `preflight_summary.json`, не доказательство скорости или качества.

`run --pilot` снова выполняет preflight, A/A и одну A/B-пару по 12 текстов на бакет.
Он проверяет связность запуска; его статус никогда не равен `screening_pass`.
Подготовка всех форм и полный preflight нужны даже в пилоте, поэтому он не гарантированно мгновенный.
Пилот не заменяет и не уменьшает последующий screening. Его архив позволяет оценить длительность.

`run` всегда заново выполняет preflight. Далее A/A 2×30 и A/B 3×400 на каждую сторону
каждого обязательного бакета, AB/BA, seed порядка 17, по 20 прогревов перед стороной.
Корпус закреплён по commit `49c2c0b069290c29d45c9c42e41cac4bea344649`, доступ без токена.
Для модели может понадобиться штатная авторизация Hugging Face; не вписывать секреты в JSON.

Все стороны работают в последовательных отдельных процессах. В каждом заново загружается
модель и готовится backend. Это исключает наследование патчей/аллокаций, но раздвигает пары
по времени; timestamps, setup и дрейф сохраняются. Компиляция и экспорт не входят в latency.
Раздельно записываются загрузка модели, валидация входов, экспорт/создание ORT-сессии,
проверка размещения ORT, прогрев форм (включая компиляцию) и прогрев перед измерениями.
Для HaloGuard v4 прогреваются все формы текущего worker: серия latency, два profile-входа
либо весь корпус и лимит для preflight/memory. Область записывается в `preparation_scope`.
Тексты, подготовленные тензоры или ответы внутри измеряемого пути не кэшируются.
Новая компиляция во время серии завершает её ошибкой, а не незаметно меняет показатель.

После latency идут отдельные memory-прогоны: три на вариант, в свежих процессах, весь применимый корпус.
GPU-память текущего PID опрашивается через nvidia-smi с целевым периодом 50 мс.
Фактические интервалы сохраняются; sampled peak может пропустить короткий пик.
Setup/inference отделены; сброс Torch counters не освобождает резерв и не сбрасывает ORT.
Недоступные process-memory значения не заменяются общей памятью GPU.

Отдельная стадия профиля сохраняет короткий/длинный выбранные входы, CPU/CUDA trace и таблицу операций.
FLA/compile fusion может мешать атрибуции слоя: неподтверждённая связь остаётся неизвестной.
Профили не используются как измерение обычного latency.

## Как читать результат

```bash
python tools/benchmark.py report --output benchmark_runs/halo-screening
```

Эта команда работает без Torch/GPU/сети. В каталоге есть `REPORT.md` и `summary.json`;
рядом с каталогом — ZIP, в том числе при ошибке/таймауте. Статусы:

- `screening_pass`: снижение pooled p95 строго больше 20% во всех обязательных бакетах,
  ноль смен вердиктов/нестабильных повторов и пройдены консервативные шумовые проверки.
- `rejected`: целевой эффект не достигнут либо есть изменения вердиктов.
- `inconclusive`: эффект не отделён от A/A/дрейфа, непоследователен по блокам или интервал включает отсутствие улучшения.
- `rejected_candidate_execution`: baseline preflight прошёл, кандидат не выполнился.
- `incomplete`: недостающие стадии, сбой baseline/среды или таймаут.
- `pilot_complete`: выполнен пилот, приёмка ускорения не проводилась.

Успешный `preflight` имеет статус выполнения `completed`; согласованность ответов смотреть
отдельно в `preflight_summary.json`. Ненулевые flips не маскируются успешным выполнением.

Отдельно сохраняются `speed_status`, `verdict_status`, `memory_status`, `quality_status`:
быстрый кандидат со сменами вердиктов не получает общий pass.
`quality_evaluated=false` и `independently_confirmed=false` во всех отчётах этого этапа.
P95 считается по объединённым задержкам бакета, не средним/медианой блочных p95.
Bootstrap 2000 повторов с seed 42 пересэмплирует целые пары, а не отдельные запросы.
Три блока одной VM дают слабую оценку неопределённости и не заменяют независимые сессии.
Сохраняются p50, A/A, дрейф, смены меток, Δp, logit margin и расстояние baseline до порога.

Raw данные: `latency/*/latencies.jsonl`, preflight scores, результаты каждого worker,
паспорта, source snapshot, backend evidence, память и сжатые traces. Полный корпус включён
для автономного построения отчёта. Веса, ONNX/external data, venv и credentials в ZIP не включаются;
исключённые/слишком большие файлы перечисляются в `archive_contents.json`.
После успешного worker воспроизводимые ONNX-файлы удаляются: размеры, graph/provider evidence
и список удалённых файлов сохраняются. При ошибке экспорт остаётся локально для диагностики, вне ZIP.
Лимит: 10 часов на сравнение. Прерывание VM без возможности выполнить finally может оставить
только уже записанные файлы, без последнего ZIP. Не перезапускать до получения удобного результата.

## Python-вызов для будущего CLI

```python
from u1_benchmark import run

result = run({
    "preset": "gliner_ort",
    "environment": ".u1-env",
    "mode": "screening",
    "seed": 17,
    "timeout_seconds": 36000,
}, "benchmark_runs/gliner-ort-screening")
```

Один вызов создаёт новый каталог и не перезаписывает предыдущий. GPU работает только в
дочерних процессах выбранного venv. Добавление других моделей/вариантов и API автоподбора
не входит в этот комплект; текущие presets намеренно закрыты от произвольного fallback.

CPU-тесты проверяют данные, статистику, модельную маршрутизацию на маленькой случайной
GLiNER-фикстуре, процессы, память, таймауты и архивирование. Mock compile/ORT проверяет
маршрутизацию, не CUDA-совместимость или ускорение. Финальная приёмка требует реальных T4-архивов.

## Перед публикацией: проверить прогрев всех длин

**Открытая обязательная проверка.** Сейчас `worker.execute` выбирает по одному тексту каждой
уникальной полной длины всего применимого корпуса, а `models.activate` безусловно выполняет
их перед каждой серией в новом процессе. Это включает eager baseline. В HaloGuard получается
около 846 длин; наблюдавшиеся примерно 10 минут подготовки baseline не являются доказательством
846 компиляций. Поле `shape_warmup_including_compile_seconds` измеряет весь проход, а не только
компиляцию. Необходимость такого повторного прогрева пока не обоснована.

- [ ] Для закреплённых версий FLA/Triton установить реальные ключи специализации и autotuning;
  отдельно проверить recompilation в `torch.compile(dynamic=True)`. Новая длина сама по себе
  не доказывает новую компиляцию. Сохранить ссылки на исходники и наблюдаемые события.
- [ ] Разделить полную проверку входов в preflight, проверку размещения ORT, первичную
  компиляцию/autotuning и обычный прогрев. Обосновать, что необходимо повторять в каждом
  свежем процессе и какие формы достаточно прогревать для конкретной реализации.
- [ ] Отдельным диагностическим экспериментом сравнить текущий полный и сокращённый
  обоснованный прогрев: время подготовки, события компиляции/autotuning, p50/p95 и дрейф.
  Контроль охватывает baseline и candidate; проверка только счётчика Dynamo недостаточна
  для исключения внутреннего Triton JIT/autotuning. Диагностику не включать в основной таймер.
- [ ] Перед публикацией зафиксировать решение и ограничения. Если протокол меняется,
  выпустить новую версию и повторить затронутые сравнения; старые архивы не перезаписывать
  и результаты разных протоколов не объединять. Если полный прогрев остаётся, явно указать
  его обоснование и стоимость, не называть её временем компиляции без соответствующих данных.

Критерий закрытия: есть проверяемое объяснение выбранного прогрева для каждого backend,
раздельные длительности подготовки и измерений, а отсутствие новых компиляций/autotuning
в измеряемой серии подтверждено на проверенных сценариях либо явно отмечено как непроверенное.
Этот пункт не меняет код и не прерывает текущие GPU-запуски.
