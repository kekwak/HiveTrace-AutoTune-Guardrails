# KoalaAI/Text-Moderation — узкие места и идеи оптимизации

DeBERTa-классификатор, 139M параметров, fp32, батч 1. Tesla T4 (Kaggle), torch 2.11.0+cu130, transformers 5.20.1 (`env.json`).
Ноутбук: [`notebooks/koala_profile.ipynb`](../../../notebooks/koala_profile.ipynb).

## Ключевые цифры

| Вход, токенов | p50, мс | p95, мс | GPU busy | Ядер на forward | Узкое место |
|---|---|---|---|---|---|
| 16–128 | 22.0–22.3 | 23.3–24.2 | 27–49% | 647–719 | overhead |
| 256 | 27.8 | 28.0 | 71% | 647 | переходная зона |
| 512 | 66.1 | 67.5 | 91% | 647 | compute (fp32) |

- Токенизация, копирование на GPU и обратно — меньше 2 мс даже на 512 токенах: всё время уходит в forward.
- До 128 токенов задержка не зависит от длины: время уходит на запуск ~700 ядер, а чистая работа GPU — 6–11 мс из ~22 мс.
- На 512 токенах 70% времени GPU — fp32 GEMM (`volta_sgemm`, без Tensor Cores, ~23% от пика T4 fp32), 19% — elementwise, 8% — gather относительных позиций.

Скриншоты Perfetto: `figures/perfetto_L16.png` (пустоты между ядрами на GPU-дорожке), `figures/perfetto_L512.png` (GPU занята сплошь, CPU ждёт в `4_d2h`).

## Узкие места

1. **Overhead запуска ядер (≤ 256 токенов).** Python-диспетчеризация ~700 операций на forward; CPU не успевает подавать работу, GPU простаивает больше половины времени.
2. **Мелкие GEMM на коротких входах.** cuBLAS выбирает «нарезанные» и split-K варианты (`sliced`, `splitKreduce`) — лишние ядра и низкая утилизация.
3. **fp32 на T4 (длинные входы).** Tensor Cores T4 работают только в fp16: 8.1 против 65 TFLOPS.
4. **Мелкие elementwise / reduce / gather** — 13–19% / до 9% / 4–8% времени GPU, каждое — отдельное чтение и запись памяти.

## Идеи оптимизации

| Идея | Что лечит | Ожидаемый эффект | Без потери качества? |
|---|---|---|---|
| **CUDA Graphs** по корзинам длин (16/32/64/128/256/512, паддинг до корзины) | overhead: один запуск графа вместо ~700 ядер | до ~2× на ≤ 128 токенах (нижняя граница — время ядер, 6–11 мс) | да; проверить совпадение вердиктов с паддингом |
| **`torch.compile(mode="reduce-overhead")`** | overhead + слияние elementwise | сопоставимо с CUDA Graphs плюс сокращение числа ядер | да; динамические длины → корзины или `mark_dynamic` |
| **ONNX Runtime CUDA EP**: оптимизатор графа, IO binding, `enable_cuda_graph` | overhead, слияние, лишние копии | основной кандидат для CLI на этапе 3 | да; сверить логиты |
| **Кэш относительных позиций** по длине корзины | TorchScript-вызов и gather на каждый запрос | несколько процентов | да |
| **fp16 / autocast** | вычисления на длинных входах | кратно на 512 токенах | **нет** — нужна проверка на хвостах (этап 4) |

### Как убрать overhead
- Зафиксировать формы входа (корзины длин) и захватить forward в CUDA Graph: CPU делает один запуск на запрос.
- Сократить число операций: слияние через Inductor или ORT, кэш относительных позиций.
- Убедиться, что в forward нет синхронизаций CPU↔GPU: в трейсах на forward их нет, поэтому захват в граф возможен.

### Как сделать вычисления плотнее
- Слить elementwise и reduce с соседними GEMM: меньше проходов по памяти.
- На длинных входах — fp16 GEMM на Tensor Cores, но только после проверки качества.
- После снятия overhead снова снять профиль: узким местом станут сами ядра, и тогда имеет смысл подбирать GEMM.

## Оговорки
- Нижняя граница задержки в трёх сессиях: 21.4 / 24.7 / 22.3 мс, то есть шум между запусками около ±7%. Для вывода «≥ 20% ускорения» нужны повторы и доверительный интервал.
- Перед частью прогонов GPU была тёплой (до 70 °C) — частоты не контролировались.
- Пороги классификации (GPU busy 50%, matmul 60%) — эвристика.
- GPU busy считается по разным прогонам (с профайлером и без), поэтому на 512 токенах значение может приближаться к 100% или превышать его.
