# Lossless-оптимизации инференса guardrail-моделей

Сценарий: синхронная проверка одного запроса (batch 1), цель — задержка. Замеры сняты на Tesla T4. Только оптимизации без потери качества: архитектура и веса не меняются.
«Замер» — проверено командой, «оценка» — расчёт без замера.
«Условие» — проверка в коде, а не имя модели: правило подходит любой модели, для которой она истинна. «Модели» — модели пула, у которых она истинна. Проверки реализованы в `rules/conds.py` и прогнаны на всех восьми моделях на RTX 4090.
Обозначения: `model` — загруженная torch-модель, `cfg = model.config.get_text_config()`, `base` — baseline-адаптер измерителя (подготовка входа, эталонный вызов, разбор ответа), `cap = torch.cuda.get_device_capability()`, `fp32 = all(p.dtype == torch.float32 for p in model.parameters())`.

## Главное

- **У большинства моделей GPU простаивает:** CPU не успевает запускать ядра (у HaloGuard ~14.6 тыс. ядер на запрос). Главная мера — CUDA graph (U1).
- **У decoder'ов 75–93% входа — одинаковый для всех шаблон с политикой.** Его можно посчитать один раз (C2).
- **Attention у Qwen3-моделей на T4 идёт по медленному fp32-пути** из-за GQA. Лечится развёртыванием голов KV (C1), замер ~18× на слой.
- **fp32-матмулы без tensor cores** — главное узкое место ShieldGemma и длинных входов у DeBERTa (C5).

## Безусловные — подходят любой модели

### U1. CUDA graph по корзинам длин *(в vLLM автоматом)*
- **Узкое место:** CPU запускает ядра по одному (500–14 600 на запрос), GPU в это время ждёт. GPU busy 18–61% у большинства моделей.
- **Условие:** `torch.cuda.is_available()`. Формы входа фиксирует U2, синхронизации убирает U3.
- **Модели:** все; у gliner-guard — только encoder.
- **Как:** `torch.compile(mode="reduce-overhead", dynamic=False)` или ручной `torch.cuda.CUDAGraph`. Вход дополняется паддингом до корзины (64 / 128 / 256 / 512 / 1024), на каждую корзину свой граф, все корзины прогреваются при старте. Длиннее последней корзины — обычный путь.
- **Эффект:** gliner-guard 46 → 18 мс (замер, compile). Другие модели с упором в CPU — 2–3× (оценка).
- **Проверка:** логиты на корзине против исходной модели без паддинга.

### U2. Паддинг до корзины без изменения ответа *(в vLLM автоматом)*
- **Узкое место:** само ничего не ускоряет, но без него не работает U1: граф требует фиксированной длины.
- **Условие:** включено U1.
- **Модели:** все.
- **Как:** decoder — паддинг справа, логит брать с последнего настоящего токена (причинная маска не даёт настоящим токенам видеть паддинг). Encoder — паддинг + `attention_mask`.
- **Эффект:** нет, это условие для U1.
- **Проверка:** вердикт и вероятность с паддингом против точной длины.

### U3. Убрать синхронизации CPU↔GPU *(в vLLM автоматом)*
- **Узкое место:** `.item()`, `.to()` на CPU, `if tensor:` внутри forward: CPU ждёт GPU, а CUDA graph не записывается. HaloGuard — 27 на запрос, gliner-guard — 12, HiveTraceGuard — 6 (из `generate`), OpenGuardrails — 1 на forward, Prompt-Guard — 1.
- **Условие:** во время forward под `torch.cuda.set_sync_debug_mode("warn")` есть предупреждение `called a synchronizing CUDA operation`, или эталон вызывает `generate` (синхронизация на каждом шаге). Обязательно перед U1.
- **Модели:** все, кроме KoalaAI.
- **Как:** найти через `torch.cuda.set_sync_debug_mode("warn")`. При batch 1 без паддинга передавать `attention_mask=None`, константы переносить на GPU один раз при загрузке, не использовать `generate`.
- **Эффект:** сам по себе единицы мс (оценка); главное — открывает U1.
- **Проверка:** логиты совпадают бит в бит (`torch.equal`).

### U4. Слияние мелких операций (`torch.compile`) *(в vLLM автоматом)*
- **Узкое место:** RMSNorm, RoPE, активации, residual и касты — каждая отдельным ядром. У HiveTraceGuard это 24% времени GPU и 64% запусков, у DeBERTa-моделей — до 53% времени при 512 токенах.
- **Условие:** всегда. Разрывы графа (`torch._dynamo.explain(forward)(x).graph_break_count`) уменьшают эффект: у KoalaAI их 9, у остальных 0.
- **Модели:** все.
- **Как:** `torch.compile(fullgraph=True)`, разрывы смотреть через `TORCH_LOGS=graph_breaks`. На T4 матмулы оставлять cuBLAS: Triton-GEMM там без tensor cores.
- **Эффект:** поэлементная доля меньше в 2–3×, ядер на слой ~80 → 20–30 (оценка).
- **Проверка:** логиты против eager с допуском (compile меняет порядок операций).

### U5. Меньше работы на CPU вокруг модели *(в vLLM частично автоматом)*
- **Узкое место:** шаблон, токенизация, хуки и копирование входов на каждый запрос.
- **Условие:** всегда.
- **Модели:** все.
- **Как:** `torch.inference_mode()`; модель грузить через `.to("cuda")` без хуков accelerate; токены постоянного шаблона токенизировать один раз; входы копировать через pinned-буфер.
- **Эффект:** 1–3 мс (оценка).
- **Проверка:** токены входа совпадают с исходным путём.

## Условные — зависят от модели или GPU

### C1. Быстрый attention для GQA *(в vLLM автоматом)*
- **Узкое место:** при GQA fused-ядра SDPA не запускаются, PyTorch откатывается на math-путь в fp32. У HiveTraceGuard это 48–87% времени GPU, у OpenGuardrails 10–27%.
- **Условие:** `cfg.num_key_value_heads < cfg.num_attention_heads and not getattr(cfg, "attn_logit_softcapping", None)`, и при этом `cap < (8, 0)` (T4) или torch < 2.14.
- **Модели:** HiveTraceGuard (16/8), OpenGuardrails (32/8), HaloGuard (8/2 в слоях полного attention). ShieldGemma (8/4) — нет: softcap.
- **Как:** перед SDPA развернуть KV — `k.repeat_interleave(n_rep, dim=1)`, то же для `v`. Плюс `is_causal=True` без явной маски. Убедиться, что включилось быстрое ядро: `sdpa_kernel([SDPBackend.EFFICIENT_ATTENTION])` выдаст ошибку, если нет.
- **Эффект:** 11.1 → 0.6 мс на слой при 1441 токене (замер).
- **Проверка:** логиты и вердикты против math-пути с допуском fp16.

### C2. Кэш префикса *(в vLLM автоматом)*
- **Узкое место:** постоянный шаблон пересчитывается на каждый запрос.
- **Условие:** `model.can_generate()` (causal decoder) и `n > 0`, где `n` — длина общего начала `base.prepare("Hello there")["input_ids"]` и `base.prepare("Bye now")["input_ids"]` минус 1 (последний общий токен может склеиться с текстом). Encoder не подходит: каждый токен видит весь вход.
- **Модели:** HiveTraceGuard (393 из 427 токенов), OpenGuardrails (227–290 из 306), HaloGuard (~400 из 429). ShieldGemma — общий префикс 28 из 126 токенов, условие выполняется, но политика стоит после текста и не кэшируется, выигрыш мал. Encoder'ы не подходят.
- **Как:** один раз прогнать префикс и сохранить KV-кэш, на запрос считать только хвост с текстом. У HaloGuard кэшировать ещё и рекуррентное состояние слоёв linear attention.
- **Эффект:** HiveTraceGuard 78 → ~10–20 мс вместе с U1 (оценка).
- **Проверка:** токены `префикс + хвост` совпадают с токенами полного входа (на стыке BPE может склеить токены); логиты против полного прохода.

### C3. lm_head только по нужным токенам *(в vLLM частично автоматом)*
- **Узкое место:** lm_head умножает на всю матрицу словаря (151–256 тыс. строк) ради двух токенов вердикта.
- **Условие:** `model.can_generate() and hasattr(model, "lm_head")`, и эталон делает один шаг: один forward на запрос, `generate` не вызывается или вызывается с `max_new_tokens == 1` (иначе сначала C4). Что вердикту хватает пары токенов (`safe`/`unsafe`, `Yes`/`No`), подтверждает проверка вердиктов.
- **Модели:** HiveTraceGuard, HaloGuard, ShieldGemma. OpenGuardrails — нет: категорию генерирует по полному словарю.
- **Как:** `logits_to_keep=1` (только последняя позиция), вместо всей матрицы — 2 строки: `hidden_last @ W[[id_safe, id_unsafe]].T`. У ShieldGemma применить softcap 30 к двум логитам, у HaloGuard сохранить порог 0.65.
- **Эффект:** −1.4 мс у HiveTraceGuard, −2.3 мс у HaloGuard (замер стоимости lm_head).
- **Проверка:** у HaloGuard и ShieldGemma вероятность и так считается по двум логитам — результат точный. У HiveTraceGuard штатный путь — `generate` с argmax по всему словарю: ответ совпадёт, пока самый вероятный токен — `safe` или `unsafe`, сверять на датасете.

### C4. Без `generate` для моделей, которые генерируют больше одного токена
- **Узкое место:** `generate` догенерирует категорию и делает синхронизацию на каждом шаге.
- **Условие:** `model.can_generate()`, эталон вызывает `generate` с `max_new_tokens > 1`, и вердикт по первому токену совпадает с вердиктом по полному ответу (`conds.py` сверяет smoke-строки, перед замером — весь датасет).
- **Модели:** OpenGuardrails (`safe` или `unsafe\nS5`). Для моделей с вердиктом из одного токена это то же, что U3.
- **Как:** вердикт по первому токену из одного forward. При `safe` — сразу выход. При `unsafe`, если нужна категория, догенерировать 2–4 шага из уже посчитанного KV-кэша.
- **Эффект:** `safe` 271 → 214 мс (по замерам режимов).
- **Проверка:** вердикт и категория совпадают с `generate(do_sample=False)`.

### C5. fp16 вместо fp32 — только с проверкой качества
- **Узкое место:** fp32-матмулы без tensor cores: у ShieldGemma 91–96% времени ядер, у DeBERTa-моделей — на длинных входах.
- **Условие:** `fp32 and not torch.cuda.is_bf16_supported()` (T4), forward без autocast.
- **Модели:** на T4 — ShieldGemma, KoalaAI, Prompt-Guard, gliner-guard. На RTX 4090/5090 условие ложно: там есть bf16.
- **Как:** `model.half()`, нормы и softmax оставить в fp32. Не через autocast: он перекастовывает веса на каждый вызов.
- **Эффект:** ShieldGemma 282 → ~80–110 мс (оценка).
- **Проверка:** не гарантированно без потерь, у Gemma бывают переполнения в fp16. Нет inf/NaN по слоям, вердикты 100%, |Δp| ≤ 1e-3.
- **На RTX 5090 и других GPU с bf16** для ShieldGemma, OpenGuardrails и HaloGuard пункт не нужен: они считаются в родном bf16. TF32 держать выключенным.

### C6. Attention с softcap
- **Узкое место:** в Gemma2 attention с softcap, обычный SDPA его игнорирует, поэтому сейчас eager — attention из отдельных операций.
- **Условие:** `getattr(cfg, "attn_logit_softcapping", None)` (из-за него SDPA недоступен и attention идёт через eager) и `cap >= (8, 0)`. На T4 не приоритет: attention там занимает мало.
- **Модели:** ShieldGemma.
- **Как:** FlashAttention 2.6+ или FlashInfer с softcap; `flex_attention` (на T4 медленно).
- **Эффект:** не оценён; вырастет на GPU с bf16, где linear-слои ускорятся.
- **Проверка:** логиты `Yes`/`No` против eager.

### C7. Быстрые ядра linear attention *(в vLLM автоматом)*
- **Узкое место:** без пакетов `flash-linear-attention` и `causal-conv1d` transformers молча берёт медленную реализацию: 73% времени GPU, ~90% ядер, 18 синхронизаций.
- **Условие:** `"linear_attention" in getattr(cfg, "layer_types", [])` или в `model.modules()` есть класс `*GatedDeltaNet`, и импортируется `fla` (`causal_conv1d` ускоряет свёртку, но не обязателен).
- **Модели:** HaloGuard.
- **Как:** поставить пакеты; на T4 — только fp16 (bf16-ядра FLA там не компилируются); `attention_mask=None`.
- **Эффект:** 349 → 126 мс (замер).
- **Проверка:** Δp(unsafe) ≤ 0.0023 против fp32, смен вердиктов нет (замер У1 на 300 примерах).

### C8. DeBERTa: относительные позиции
- **Узкое место:** в каждом слое на каждый запрос заново проецируются 512 эмбеддингов относительных позиций, хотя результат зависит только от весов. ~27% времени GPU у Prompt-Guard и ~30% у gliner-guard на коротком входе.
- **Условие:** `any(hasattr(m, "get_rel_embedding") for m in model.modules())` — encoder с disentangled attention (DeBERTa v1–v3), проекции относительных позиций не зависят от входа.
- **Модели:** Prompt-Guard, gliner-guard (v3), KoalaAI (v1).
- **Как:** v3 — посчитать проекции один раз при загрузке (патч attention-слоя). v1 — позиции зависят от длины, кэшировать по корзинам.
- **Эффект:** до ~27–30% времени GPU на коротких входах (оценка по профилю).
- **Проверка:** логиты совпадают бит в бит.

### C9. Веса в низкой точности один раз вместо autocast
- **Узкое место:** autocast перекастовывает веса fp32 → fp16 на каждый вызов (319 копий на forward).
- **Условие:** `fp32`, и forward-pre-hook видит `torch.is_autocast_enabled("cuda")` с `torch.get_autocast_dtype("cuda")` fp16 или bf16.
- **Модели:** laya.
- **Как:** `model.half()` один раз вместо autocast.
- **Эффект:** проявится только вместе с U1: сейчас копии прячутся в простоях GPU.
- **Проверка:** против autocast-версии, вердикты 100%.

### C10. ONNX Runtime для encoder'ов
- **Узкое место:** накладные расходы PyTorch на коротких входах.
- **Условие:** `not model.can_generate()` (encoder). Разрывы графа у U4 повышают приоритет.
- **Модели:** gliner-guard, KoalaAI, Prompt-Guard, laya.
- **Как:** экспорт в ONNX, CUDA EP + IO binding + `enable_cuda_graph`, по сессии на корзину.
- **Эффект:** gliner-guard против compile: 18 → 9.8 мс на коротких, но 46 → 50 мс на длинных (замер). Выбирать по длине входа.
- **Проверка:** логиты против PyTorch.

### C11. Мелочи cuBLAS и памяти
- **Узкое место:** мелкие GEMM на коротких входах, фрагментация памяти при многих корзинах.
- **Условие:** включено U1.
- **Модели:** все.
- **Как:** длины корзин кратны 8 или 64; попробовать `preferred_blas_library("cublaslt")` и `expandable_segments:True`.
- **Эффект:** не оценён — мерить.
- **Проверка:** логиты с допуском.

### C12. Слить Q/K/V и gate/up в одну матрицу *(в vLLM автоматом)*
- **Узкое место:** 3 отдельных GEMM на Q/K/V и 2 на gate/up в каждом слое — мелкие матрицы и лишние запуски.
- **Условие:** есть модуль `m`, у которого все атрибуты одной из групп — `nn.Linear` с одинаковым наличием bias: `q_proj/k_proj/v_proj`, `gate_proj/up_proj`, `query_proj/key_proj/value_proj`, `in_proj_qkv/in_proj_z/in_proj_b/in_proj_a`.
- **Модели:** все, кроме laya (у ModernBERT уже слиты `Wqkv` и `Wi`) и KoalaAI (у DeBERTa v1 QKV уже в одном `in_proj`).
- **Как:** склеить веса при загрузке, один GEMM, результат разделить через `split`.
- **Эффект:** единицы процентов (оценка).
- **Проверка:** логиты с допуском: не бит в бит, потому что cuBLAS выберет другое ядро.

### C13. Число генерируемых токенов как у эталона
- **Узкое место:** движок (vLLM и др.) по умолчанию генерирует до EOS или `max_tokens`, хотя эталону нужен один токен: лишний шаг decode и синхронизация.
- **Условие:** `model.can_generate()`, и эталон вызывает `generate(max_new_tokens=1)` или модель переносится на движок, у которого `max_tokens` по умолчанию больше 1.
- **Модели:** HiveTraceGuard. HaloGuard и ShieldGemma — только при переносе на такой движок: их эталон и так один forward. У OpenGuardrails — C4.
- **Как:** брать `max_new_tokens` и стоп-условия из эталонного конфига модели, а не умолчания движка (в vLLM — `SamplingParams(max_tokens=1)`). С одним токеном остаётся только prefill, и становится применим C3.
- **Эффект:** минус минимум один шаг decode, единицы мс (оценка).
- **Проверка:** выход совпадает с эталоном. Если эталон ждёт EOS и парсер смотрит на полный текст — пункт не применять.
