# Общий корпус скорости У1

Точка входа: `python -m speed_dataset`. Это подготовка данных на CPU, не измеритель скорости.
Весов, инференса, quality-метрик, квантования и автоматической публикации здесь нет.
Исторический `experiments/data.py` и результаты не меняются.

## Решение на следующий выпуск: модельные бакеты, 31 октября 2026

**Реализовано отдельным форматом 3 / корпусом v4; CPU-сборка и текущие статусы описаны в
[инструкции передачи](u1_handoff.md#корпус-и-модельные-бакеты).** Для следующего выпуска отказываемся
от пересечения одинаковых бакетов между моделями. Опубликованный v3, его индексы,
контрольные суммы и результаты экспериментов остаются неизменными. Инструкции сборки
ниже пока описывают существующую реализацию с пересечениями, не новый алгоритм.

- Общим остаётся исходный корпус сообщений с устойчивыми ID. В нём нужны форматы
  `user-only`, `assistant-only` и `user+assistant`.
- Подготовка входа соответствует документации конкретной модели на HF. Для энкодера
  при наличии assistant берём только его текст, без user; для user-only берём user.
  Для декодера используем предусмотренный моделью способ подачи сообщений.
- Бакет назначается по **полной фактической длине подготовленного входа токенизатором
  этой модели**, включая prompt, template/schema и специальные токены.
  Границы сохраняются: B1 1–512, B2 513–1024, B3 1025–2048, B4 2049–4096.
- Один исходный ID может попадать в разные бакеты у разных моделей. Индексы и выбранные
  списки ID бакетов становятся модельными; совпадения бакета между моделями не требуем.
- При отборе стремимся к широкому покрытию **доступных** длин внутри каждого бакета.
  Модель с обязательным длинным промптом не обязана покрывать недостижимые короткие входы.
  Фактические распределения длин показываем в отчёте; одинаковый номер бакета сам по себе
  не означает одинаковую нагрузку или состав текстов у разных моделей.
- Лимит проверяем после полной подготовки. Неподдерживаемые входы явно отмечаем,
  не обрезаем и не дополняем padding ради попадания в бакет.
- **Baseline и кандидат одной модели получают строго одинаковые ID, подготовленные
  входы и порядок запросов.** Изменение реализации не меняет выборку для сравнения.

В новом пути OpenGuardrails 0124 использует собственный шаблон и только user-only;
HaloGuard оценивает последний user, ShieldGemma требует user-контекст для ответа.
Подробная матрица ограничений находится в инструкции передачи. Историческая реализация
с пересечениями ниже остаётся доступна для старых экспериментов. Не переносить старые
проценты ускорения на новую выборку. Новая версия не опубликована автоматически.

## Контракт опубликованных версий v1–v3

| Бакет | Полный вход | Модели | Состав выбранных текстов |
| --- | --- | --- | --- |
| B1 | 1–512 | Все восемь из `speed_dataset/contracts.json` | 150 Wikipedia EN + 150 Wikipedia RU + 50 synthetic EN + 50 synthetic RU |
| B2 | 513–1024 | HaloGuard, HiveTraceGuard-Pro, OpenGuardrails, ShieldGemma | Такой же |
| B3 | 1025–2048 | Те же четыре декодера | Такой же |
| B4 | 2049–4096 | Те же четыре декодера | Такой же |

Все модели бакета получают одинаковые исходные байты текста. Учитывается полный вход с prompt,
template/schema и специальными токенами. Токены разных моделей не обязаны совпадать; внутри
baseline/candidate одной модели должны совпадать ID и маски, сверяемые по индексам.
Нельзя добирать недостающие строки дубликатами, padding, усечением или исключением модели.

Часть полного входа уже занята политикой: при проверке пустого текста получилось 397 токенов
HaloGuard, 422 HiveTraceGuard-Pro, 290 OpenGuardrails и 126 ShieldGemma. Поэтому B1 для декодеров
может оказаться узким по фактическим длинам. Это не ошибка и не равномерное покрытие 1–512.

У Laya используется штатная подготовка SDK, но для подсчёта наблюдаем длину **до** его усечки;
выход за 512 даёт unsupported. Для каждого принятого текста дополнительно сравниваются token IDs
с обычной подготовкой SDK. Конфигурация головы не меняется.
GLiNER использует настоящий `SchemaTransformer`, `safety=[safe,unsafe]`, `max_len=None`.
Его процессор иногда дописывает точку, в том числе для пустого текста. Исторический адаптер
отклоняет изменение `original_texts`: сохраняем это правило и исключаем такие строки с причиной
`processor_changed_text`, а не исправляем текст отдельно для GLiNER.

## Установка

Работать из корня репозитория. Нужны Python 3.12/3.13 и CPU-доступный PyTorch для процессоров
GLiNER/Laya. GPU не нужен. Не устанавливать общий CUDA-lock ради токенизации.
Создайте отдельный venv; если PyTorch уже установлен в notebook-runtime, его можно использовать:

```bash
python -m venv --system-site-packages .venv-speed
.venv-speed/bin/python -m pip install -r speed_dataset/requirements.txt
```

Если PyTorch отсутствует, установите CPU-сборку по официальной инструкции PyTorch в этот venv.
Рецепт не обновляет CUDA PyTorch принудительно. Перед индексацией проверяются точные версии
Transformers 5.20.1, tokenizers 0.23.3, huggingface-hub 1.33.0 и, для соответствующих моделей,
GLiNER2 2.1.0 / Laya 0.3.20. Несовпадение останавливает индексацию.
Нужен доступ HF к ShieldGemma; токен используйте через штатный `hf auth login` либо `HF_TOKEN`,
не вставляйте его в исходники или notebook. Для выбранного публичного зеркала Llama токен не требуется.

## Пул → Индексы → Пересечения

```bash
.venv-speed/bin/python -m speed_dataset pool data/speed/rebuild12000
.venv-speed/bin/python -m speed_dataset index data/speed/rebuild12000 --model halo
```

Повторить `index` с `hive`, `open`, `shield`, `gliner`, `koala`, `laya`, `llama`. Это независимые CPU-операции.
Каждая сохраняет `.meta.json`, `.jsonl` и, при прерывании, `.partial`; незавершённые индексы
не принимаются. Контрольные примеры проверяют подготовку против адаптеров/SDK либо точных
вызовов токенизации из notebook коллег; это не проверка нейросетевых вычислений.

```bash
.venv-speed/bin/python -m speed_dataset finalize data/speed/rebuild12000
.venv-speed/bin/python -m speed_dataset package data/speed/rebuild12000
```

`finalize` возвращает код 2 при `not_ready`, сохраняя отчёт и уже готовые B2/B3/B4.
Отсутствующий Llama не заменяется похожим tokenizer. Для B1 можно видеть **предварительное**
пересечение доступных моделей, но его ID не экспортируются как готовый бакет.
Если не хватает квоты, создать новый каталог с `pool --size 24000`, затем 36000 или 48000,
заново индексировать и проверить пересечения. Для экономии CPU можно добавить к `index`
`--reuse data/speed/rebuild12000`: повторно используются только строки с тем же SHA256 текста,
после проверки старого пула, полного индекса, версий, исходника подготовки и всех tokenizer-assets.
Новый индекс всё равно получает хеш нового пула; старый индекс напрямую не принимается.
Старые файлы не перезаписываются.
При дефиците на 48 000 остановиться и изучить причины; квоты и контракт не ослабляются автоматически.

## Необязательное Воспроизведение Llama Коллегой

Сгенерировать актуальный пакет: `python -m speed_dataset package data/speed/v3`.

Передать два файла из `handoff/`: `llama_index_cpu.ipynb` и `llama_index_request.zip`.
Notebook самостоятельный: проверяет хеш архива, создаёт отдельный CPU-venv,
устанавливает только tokenizer-зависимости и индексирует общий пул. Включить Internet, GPU выключить.
Архив содержит пул, исходники и контракты, **не** HF cache, credentials, веса или чужие результаты.
Используется закреплённое зеркало hipocap из текущего контракта. HF token не запрашивается;
неявная передача токена отключена. Архивные notebooks v1/v2 имеют другой контракт и не подходят.

Полученный `llama_index_response.zip` импортировать так:

```bash
.venv-speed/bin/python -m speed_dataset import-index data/speed/v3 /path/to/llama_index_response.zip
.venv-speed/bin/python -m speed_dataset finalize data/speed/v3
```

Перед импортом проверяются состав архива, полный набор ID, хеш пула, revision/contract,
исходник подготовки, версии, parity и хеш файла индекса. Индекс другого пула не принимается.
После изменения исходников подготовки нужно заново индексировать, собрать handoff и переслать его.

## Артефакты и Лицензии

`latest.json` указывает на последний отчёт в `releases/<fingerprint>/`:
`REPORT.md`, `manifest.json`, `corpus.jsonl` и готовые `B*.ids.json`.
В manifest есть гистограммы, min/median/p95/max, квоты, размер пересечения и причины отказов.
`ready` всего комплекта v3 требует 1600 уникальных текстов и всех восьми индексов.
До этого `corpus.jsonl` может содержать только 1200 текстов готовых B2/B3/B4.

Источник: [Wikimedia Wikipedia, 20231101](https://huggingface.co/datasets/wikimedia/wikipedia/tree/b04c8d1ceb2f5cd4588862100d08de323dccfbaa),
ревизия `b04c8d1ceb2f5cd4588862100d08de323dccfbaa`, первые закреплённые EN/RU parquet-shards.
Их загрузка занимает около 1 ГБ в HF cache; хеши файлов сохраняются.
Фрагменты берутся по границам слов до модельной токенизации. Не более одного фрагмента на статью
в пуле предотвращает почти одинаковые перекрывающиеся окна одного источника. Точные повторы
удаляются; это не полноценная семантическая дедупликация всего корпуса.
Для каждой записи сохранены статья, URL, история авторства, символьные позиции и хеш исходной статьи.
Лицензии источника: CC-BY-SA-3.0/GFDL; при передаче сохранять атрибуцию и условия источника.
Синтетика детерминированная, CC0-1.0, без внешних LLM и повторения одной фразы до нужной длины.

Распределение 50/50 EN/RU и 75/25 Wikipedia/synthetic выбрано экспериментатором. Wikipedia-фрагменты
не обязательно похожи на запросы пользователей; синтетика ограничена заданными шаблонами.
Отбор пересечения дополнительно смещает распределение в сторону совместимых длин и форматов.
Никакой production-репрезентативности, оценки редких атак или качества по разметке не заявляется.
