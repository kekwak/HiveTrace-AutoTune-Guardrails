слайда 16:9 без обложки для общей презентации. Ниже тезисы и полный текст выступления,

## Слайд 1. У1. Среда и измеритель

- Один консольный измеритель: восемь baseline-адаптеров, три готовых comparison-пресета,
  внешняя конфигурация/артефакт, отдельный quality-этап, offline report/table.
- **151 CPU-тест без ошибок и пропусков**; отдельный smoke **8/8 моделей на T4 GPU 0**.
  Проверены 40 полных запросов на применимых бакетах, A→B→A, лимит/превышение,
  реальный CUDA backend и память. Архив проверен, восемь отчётов пересобраны offline.
- Целевая среда команды — RTX 4090/5090; её проверяют владельцы. T4-smoke не означает
  успешный RTX benchmark. Настоящее квантование и качество по разметке пока не проверены.

Доказательство: [validation 4 ноября](../results/u1_handoff/2026-11-04-review-smoke/validation.json),
[хеши исходников](../results/u1_handoff/2026-11-04-review-smoke/source_manifest.json).
Количество таймингов smoke не является размером полного baseline.

## Слайд 2. Корпус и бакеты по моделям

- Один пул **12000 ролевых записей EN/RU**, форматы user / assistant / user+assistant.
  Модели получают только поддерживаемые ими роли и контекст, согласно закреплённой подготовке.
- **20 модельных бакетов по 400 уникальных эффективных входов**:
  B1 1–512 для четырёх энкодеров; B1–B4 до 4096 для четырёх декодеров.
  Бакет определяется полной длиной после template/schema и специальных токенов.
- Один ID может иметь разные бакеты у разных моделей. Идентичность обязательна
  именно внутри baseline/candidate-пары: ID, сообщения, token IDs/маски и порядок.
- Отбор стремится покрывать широкий диапазон длин; дефициты интервалов видны в отчёте,
  padding и скрытой усечки нет. Это speed-нагрузка, не размеченный safety-бенчмарк.
- Open: веса 0124 + task-промпт 2510, отдельный пересчитанный индекс.
  Исторический native-v4 не переписывается; остальные семь индексов не меняются.

Доказательства: [сверка входов](../results/u1_handoff/2026-11-01-open-shield/input_validation.json),
[распределения исходного v4](https://huggingface.co/datasets/vXofi/guardrails-speed-en-ru/blob/7324b8823ded971c05076e0c7f4ace5d9b867863/REPORT.md),
[профиль Open](../configs/data/role_speed_open_task.json).

## Слайд 3. Протокол сравнения

- Основная метрика — pooled p95 полного пути сообщения → scores/вердикт на CPU.
  Токенизация внутри таймера; batch/concurrency 1. P50 — дополнительный показатель.
- Одна VM внутри сравнения, одинаковый порядок в паре; A/A две пары ×30,
  A/B три пары ×400 на сторону и бакет, 20 прогревов, чередование AB/BA.
- 95%-интервалы по целым парным блокам, 2000 bootstrap-повторов; A/A и дрейф
  защищают от заявления ускорения на уровне шума. Три блока не равны независимым сессиям.
- Память отдельно: три свежих процесса на вариант, setup/inference-окна,
  process GPU peak и Torch counters раздельно; short/long-профили вне latency.
- Инженерное изменение: снижение p95 **строго >20% во всех обязательных бакетах**,
  ноль flips/нестабильных повторов и пройденные шумовые проверки.
  Параметрическое — >10%; для квантования flips и macro по бакетам показываются отдельно,
  без автоматического решения о качестве.

Источник методики и реализации: [актуальный протокол](measurement_protocol_v1.md),
[статистика](../u1_benchmark/statistics.py), [формирование расписания](../u1_benchmark/runner_v2.py).
Совпадение вердиктов на speed-наборе не заменяет качество на разметке.

### Слайд 1. У1. Среда и измеритель

Моя часть проекта: среда, единый скрипт измерений и правила сравнения конфигураций.

Скрипт поддерживает восемь моделей. Он измеряет полный запрос, память процесса и изменения вердиктов. Оценку на размеченных данных можно запустить отдельно. Интерфейс для неё готов, сам набор готовит другой участник.

Зависимости закреплены в lock-файле, установка идёт в отдельное окружение. В архиве запуска остаются конфигурация, версии, входы, сырые замеры и диагностика ошибок. Через внешний адаптер можно подключить другую реализацию или готовую квантованную модель без правок измерительного кода.

После последних исправлений мы прогнали 151 CPU-тест без ошибок. Короткий GPU-smoke прошли все восемь моделей на T4. Проверили входы, предельную длину, повторяемость ответов и работу на GPU. Полные замеры на 4090 и 5090 дальше выполняют участники, которые работают с соответствующими моделями. Результаты этих устройств будем группировать отдельно.

### Слайд 2. Корпус и бакеты по моделям

Для скорости мы собрали общий пул из двенадцати тысяч сообщений на русском и английском. В нём есть запросы, отдельные ответы и пары запрос–ответ. Каждая модель получает поддерживаемый ею формат по закреплённому шаблону.

Длину считаем после всей подготовки, включая системную инструкцию и специальные токены. Энкодеры проверяем в первом бакете до 512 токенов. У четырёх декодеров обязательны все четыре бакета, до 4096.

На каждую модель и бакет выбираем четыреста разных подготовленных входов. Различия в контексте, который модель всё равно игнорирует, не создают новый пример. Стараемся покрывать весь доступный диапазон длин. Нехватку отдельных интервалов показываем в отчёте, padding и обрезание текста для заполнения бакета не используем.

Списки разных моделей могут отличаться. Внутри сравнения одной модели baseline и кандидат получают те же ID, токены, маски и порядок. После смены шаблона пересчитываем индекс. Например, для OpenGuardrails мы сделали это под согласованный task-промпт 2510 с весами 0124.

### Слайд 3. Протокол сравнения

Основная метрика: p95 полного запроса. В таймер входят подготовка сообщения, токенизация, вычисление и получение вердикта на CPU. Batch и concurrency равны единице. Загрузку, экспорт, компиляцию и профилирование измеряем отдельно.

На одной VM сначала сравниваем baseline с самим собой: две пары по тридцать запросов на сторону. Так оцениваем шум через A/A. Затем делаем три пары baseline–candidate по четыреста запросов в каждом бакете. Порядок сторон чередуем, перед каждой стороной выполняем двадцать прогревов.

P95 считаем по объединённым измерениям. Для интервала пересэмплируем целые парные блоки. Выигрыш должен превышать A/A-разброс и дрейф контроля, а все блоки должны показывать ускорение. Этот интервал описывает одну сессию. Для другой машины замер потребуется повторить.

Для замены реализации требуем снижение p95 строго больше двадцати процентов в каждом обязательном бакете и ноль изменённых или нестабильных вердиктов. Для настройки параметров порог десять процентов. У квантования отдельно показываем долю изменённых вердиктов. Его качество будем оценивать на размеченных данных по согласованному правилу.

Память измеряем в свежих процессах, отдельно от скорости. Для ORT учитываем весь GPU-процесс: счётчики PyTorch видят только его часть.

### Слайд 4. GPU-приёмка измерителя

Для GPU-приёмки тогдашней версии измерителя мы взяли готовые конфигурации GLiNER compile, ORT и HaloGuard FLA. На них проверили полный цикл: парные замеры, память, профили и сохранение архива.

GLiNER прошёл скоростные критерии, а FLA показал устойчивое замедление. На этом случае исправили обработку отрицательного результата в отчёте: воспроизводимое замедление получает отказ. Архивы проверили, отчёты пересобрали без повторного GPU-запуска.

Дальше участники снимают baseline своих моделей на 4090 и 5090 текущей версией скрипта. Я проверю полноту архивов и соберу общую таблицу.
